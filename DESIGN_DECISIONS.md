# Design Decision Record — Contract-Driven Data Quality Monitor

Living document. Every architecture/design decision gets an ADR entry below as it is
made: context, decision, alternatives, consequences. Status markers:
`[implemented]` = code exists, `[decided]` = agreed but not yet built, `[open]` = undecided.

At submission time this file (plus README) serves as the "Design Decision Record"
deliverable from section 5 of the brief.

---

## 1. Vision & scope

Turn data contracts (ODCS v3.x YAML) into the single source of truth for "good data":
AI agents create contracts (human-approved), execute the contract's quality rules
against SQL sources, visualise issues with history, notify owner/steward from the
contract, and publish a quality score to a (simulated) marketplace.

MVP line: capabilities A–D end-to-end on the seeded SQLite dataset; E (issue
resolution) only if time permits.

## 2. Target architecture (as agreed)

```
[User / Scheduler Trigger]
            |
            v
  [0. Orchestrator (Supervisor)]   <- deterministic Python router, not an LLM
            |
   +--------+--------+-----------+------------------+
   |        |        |           |                  |
   v        v        v           v                  v (optional)
[A1        [A2       [A3         [A4                [A5
Contract   Quality   Metrics &   Notify &           Issue
Architect] Executor] Insights]  Marketplace]       Resolver]
   |                                        |           |
[HITL gate:                          [HITL gate:
 approve contract]                   approve fix before
                                     any write-back]
```

Agents communicate through a shared SQLite "blackboard" (tables: `contracts`,
`runs`, `check_results`, `issues`, `notifications`, `marketplace_entries`), not
by passing messages.

## 3. Agent personas

| # | Agent | Goal | Inputs → Outputs | Tools | Guardrails | HITL |
|---|---|---|---|---|---|---|
| A1 | Contract Architect | Draft an ODCS v3.x contract per table | schema (introspected) + business context → contract YAML | read schema, validate ODCS, write contract | contract must validate against ODCS v3.x; cannot activate itself | human approves before `status: active` |
| A2 | Quality Executor | Run contract rules against SQL, store history | active contracts → run + per-rule results | run SQL (read-only), insert results | may only execute rules present in an *active* contract; read-only on source tables | none |
| A3 | Metrics & Insights | Aggregate results into dashboard + trends | runs/results → static HTML dashboard + JSON | run SQL, write files | read-only; no new rules | none |
| A4 | Notify & Marketplace | Actionable notification + marketplace score | issues + contract → notification file + marketplace.json | write files/JSON | may only notify owner/steward addresses from the contract; channel simulated | none |
| A5 | Issue Resolver (optional) | Suggest root cause/fix | issue → suggestion + proposed action | run SQL, read contract | never writes to source data without recorded human approval | human accepts/rejects/closes |

## 4. Decision log (ADRs)

### ADR-01 — Dataset: self-built fictitious banking DB in SQLite, generated by a script
- Status: implemented (`data/seed_dataset.py`, `data/banking.db`)
- Context: brief says "we provide no data — create your own". Needs to be reproducible for the demo.
- Decision: 5 related tables (`customers`, `accounts`, `transactions`, `loans`, `cards`) with FK relationships; base data deterministic (`random.Random(42)`); defects inserted explicitly and commented with defect IDs.
- Alternatives: download a benchmark (e.g. a public banking dataset); Excel files.
- Consequences: + fully reproducible, defects known by construction, SQLite needs no server (fits low hardware); − must self-document that data is fictitious; − FKs declared but not enforced at insert time (SQLite default), which is what allows orphan-FK defects to exist — the DQ layer must catch them.

### ADR-02 — Defect seeding & manifest: 28 defects / 36 defective rows, counts measured not asserted
- Status: implemented (`data/defect_manifest.csv`)
- Context: brief requires ≥10 defects and a defect manifest (table, column, defect type, rows affected).
- Decision: 28 defects across 7 dimensions (completeness, uniqueness, validity, consistency, timeliness, accuracy, integrity). Each defect has a SQL query; `rows_affected` in the manifest is the actual `COUNT(*)` from that query after seeding.
- Alternatives: hard-code expected counts in the manifest.
- Consequences: + manifest can never drift from the data; + each defect is provably detectable by one query (verified by spot checks); − manifest queries must be kept in sync with contract rules later.

### ADR-03 — Fixed as-of date for all time-based checks
- Status: implemented (`AS_OF = "2025-06-30"` in seed script; contract rules will use the same)
- Context: first manifest run counted 6 "expired but active" cards instead of 1, because "now" had moved past the expiry dates of clean cards — clean data aged into defects.
- Decision: all time-based rules (future dates, expiry, under-18) evaluate against a fixed as-of date, not wall-clock now.
- Alternatives: use `date('now')`; refresh the dataset on every run.
- Consequences: + reproducible detection report (found/missed/false-positive comparison is stable over time); − in production the product would use run timestamp; noted as a deliberate demo simplification. The product itself will stamp each run with its own timestamp — only the seeded manifest uses the fixed date.

### ADR-04 — Orchestrator is deterministic Python, not an LLM
- Status: decided (matches user's diagram)
- Context: the brief demands an agentic implementation, but also rewards "deterministic code over an LLM on purpose"; hardware is low/medium; the demo must run reliably from the README.
- Decision: the Orchestrator is a plain Python router over a fixed pipeline (contract → run checks → metrics → notify, plus optional resolve), with per-contract schedules read from the contract SLA. LLMs live only inside agents A1/A5 at the fuzzy steps (drafting contract prose, wording/root-causing issues). All routing, rule execution, aggregation and publishing is deterministic code. Agent-to-agent state goes through SQLite (see ADR-11).
- Why not an LLM supervisor:
  1. There is nothing to decide at the top level. The flow is fixed by the brief — a DAG, not a judgment call. An LLM there adds variance, not value.
  2. Guardrails become structural. "Only active contracts", "read-only SQL on sources", "HITL before any write-back" are enforced by code. Prompts are probabilistic; code is not.
  3. Reproducibility. Same inputs → same run, every time; graders re-running from the README get identical behaviour, no flaky demo.
  4. Cost and latency. Zero tokens and zero model latency for orchestration; nothing extra to run on weak hardware.
  5. Debuggability. A `steps` log table plus normal Python tracebacks. An LLM supervisor's choices are opaque and can loop or hallucinate steps.
- When an LLM supervisor would make sense: open-ended, dynamic workflows with real exceptions — not our case.
- Super simple example:

  ```python
  # orchestrator.py — no LLM anywhere in this file
  STEPS = [contract_architect, quality_executor, metrics, notifier]  # fixed order

  def main(trigger="manual"):
      for contract in due_contracts(trigger):      # contracts table: status=active, schedule due
          for step in STEPS:
              step.run(contract)                   # each agent reads/writes SQLite; A1 blocks on human approval
              log_step(contract, step.name, "ok")
  ```
- Alternatives: LLM supervisor deciding the next step dynamically; heavy agent framework (LangChain/CrewAI).
- Consequences: + reliable, cheap, auditable, structurally safe; − the top level looks less "autonomous" (accepted: autonomy lives inside each agent's tool-calling loop). Framework skipped deliberately — a hand-rolled loop is lighter and easier to audit.

### ADR-05 — LLM access: agents call the Mistral API at runtime; Vibe (this assistant) writes the code
- Status: decided; `MISTRAL_API_KEY` already present in environment
- Context: user subscribes to Mistral AI Pro; hardware is low/medium; brief allows any LLM with full disclosure.
- Decision: runtime agent LLM = Mistral API, model `mistral-small-latest`, endpoint `https://api.mistral.ai/v1/chat/completions` with tool calling; HTTP via stdlib `urllib.request` (no `requests` installed). Coding of the framework done by Mistral Vibe — disclosed. Fallback if API quota runs out: same code against local Ollama (`qwen2.5:3b`, Q4, CPU-only) by swapping base URL + model.
- Alternatives: local-only models from the start; other APIs (Groq/Gemini free tiers).
- Consequences: + no local GPU/RAM pressure, cheap per run; + disclosure is simple ("agents use Mistral small; Vibe wrote the code"); − needs internet + API key at runtime; − cost per run must be tracked (see §6). `pyyaml` is the only pip install needed (contracts are YAML).

### ADR-06 — Guardrail: contracts drive all checks; no rules hard-coded outside contracts
- Status: decided
- Context: capability B explicitly: "Contracts drive the checks — no rules hard-coded outside the contract."
- Decision: Quality Executor compiles each contract's `quality.rules[]` into SQL at run time; unknown rule types fail the run loudly (and are reported as a contract problem, not silently skipped). LLM is never asked to invent rules — Triage/Resolver agents only describe and prioritise what the Executor flagged.
- Alternatives: LLM writes SQL per run (flexible but unaccountable, costlier).
- Consequences: + auditable, deterministic, cheap; + directly answers the brief's "prevent agents from inventing rules" question; − rule vocabulary must be designed up front (ODCS-aligned rule types).

### ADR-07 — HITL gates exactly where the brief demands human approval
- Status: decided
- Context: capability A requires human review before a contract becomes active; capability E forbids writes to source data without explicit human approval.
- Decision: two HITL gates — (1) after A1 drafts a contract, `ask_human()` blocks until approve/reject (stored in DB; `--auto-approve` flag for the recorded demo); (2) A5's proposed fix requires accept/reject/close before any write-back.
- Alternatives: no gates (rejected — violates brief); gates on every check run (too noisy).
- Consequences: + directly satisfies the brief; + approvals are auditable in DB; − demo needs a scripted approval path (`--auto-approve`) for the recording.

### ADR-08 — Notifications & marketplace are simulated as files
- Status: decided
- Context: capability D allows simulated channels ("a generated page or JSON catalogue").
- Decision: A4 writes `out/notifications/<issue_id>.json` (to owner+steward from the contract) and updates `out/marketplace.json` with per-data-product quality status/score. A3 renders a static `out/dashboard.html`.
- Alternatives: real email/Slack webhook; hosted marketplace page.
- Consequences: + zero infra, works offline, easy to show in demo; − must state clearly in DDR that channels are simulated per the brief.

### ADR-09 — Detection report produced by deterministic diff against the defect manifest
- Status: decided
- Context: Task 1 requires comparing detected issues with the defect manifest (found / missed / false positives); deliverable is an Excel tab (seeded defect, rule, detected Y/N, severity).
- Decision: `compare_to_manifest.py` matches `issues` from the latest run to `defect_manifest.csv` by (table, column, defect_type) and emits `out/detection_report.csv` ready to paste into Excel, with an honest miss/false-positive analysis printed.
- Alternatives: manual comparison in Excel.
- Consequences: + reproducible, honest reporting; − matching is by rule metadata, so rule naming must be 1:1 with manifest defect types.

### ADR-10 — Tooling: Python 3.13 + SQLite + stdlib HTTP; only `pyyaml` installed via pip
- Status: implemented for data layer; agents pending
- Context: low/medium hardware, minimal deps preferred.
- Decision: no web framework, no ORM, no `requests`; `urllib.request` for the Mistral API; SQLite via stdlib `sqlite3`; dashboard = static HTML file.
- Alternatives: FastAPI + requests + ORM.
- Consequences: + runs anywhere, boots instantly, nothing to break on demo day; − more boilerplate, acceptable at this scale.

### ADR-11 — Agents communicate through a SQLite "blackboard", not messages
- Status: decided
- Context: agents must hand work to each other (A2's results → A3's dashboard; issues + contract → A4's notifications) without tight coupling.
- Decision: no agent calls another agent or passes Python objects. Each agent reads its inputs from and writes its outputs to shared tables in one SQLite file (`contracts`, `runs`, `check_results`, `issues`, `notifications`, `marketplace_entries`, `steps`). It is a shared whiteboard everyone writes on.
  Flow: A1 inserts a contract row (after the HITL gate) → A2 inserts `runs` / `check_results` → A3 SELECTs them to render the dashboard → A4 SELECTs `issues` JOIN `contracts` to find owner/steward, then writes `notifications` + `marketplace.json`.
- Why:
  - Decoupling — re-run or retry a single step without redoing the whole pipeline.
  - Free history — results are append-only, so the trend view of capability C is just a query over past runs.
  - Auditability — approvals and decisions are rows you can inspect.
  - Crash-safety — if the process dies mid-pipeline, resume from the last completed row in `steps`.
  - Zero infra — no message broker, no server; one file DB fits low hardware.
- Alternatives: direct agent-to-agent calls or message passing (RabbitMQ / Redis / framework message buses).
- Consequences: + simple and robust; − requires discipline: table schemas are defined once in `schema.sql` and each agent only writes its own tables.

### ADR-13 — Contracts validated against the official ODCS v3.0.0 JSON Schema (vendored)
- Status: implemented
- Context: the brief requires contracts "compliant with ODCS v3.x" and graders check "contracts valid against the ODCS schema".
- Decision: the official schema from bitol-io/open-data-contract-standard (`schema/odcs-json-schema-v3.0.0.json`) is vendored at `src/dq/odcs-json-schema-v3.0.0.json` and every `contracts/*.yaml` is validated against it with the `jsonschema` library at `python run.py sync` time, plus semantic checks (the contract's table and columns must exist in the source DB, rule names unique). Rules use ODCS-native constructs: `type: library` rules (nullCount, duplicateCount) sit at property level (field implied), `type: sql` rules carry a `query` with `${table}` / `${asOf}` / `${asOfMonth}` placeholders. 28 rules across 5 contracts = exactly the 28 manifest defects.
- Schema learnings (hit while building): top-level `description` must be an object (`purpose`/`usage`/`limitations`), not a string; `logicalType` enum has no `timestamp`; the `dimension` enum has no `validity`/`integrity`, so manifest `validity` maps to ODCS `conformity` and `integrity` to `consistency` (manifest comparison is by table/column/defect_type, so naming differs safely).
- Consequences: + contracts provably schema-valid offline; + if an approved contract's YAML changes, `sync` flips it back to `draft` (re-approval, HITL); − the vendored schema pins us to v3.0.0 specifically (brief allows any v3.x).

### ADR-14 — Local API key via a gitignored `.env`, loaded tolerantly
- Status: implemented
- Context: the Vibe VS Code extension authenticates via OAuth session and stores **no** API key (`~/.vibe/config.toml` contains none — checked). Each shell is a fresh process, so `export MISTRAL_API_KEY=...` does not persist.
- Decision: `config.py` loads a repo-root `.env` (in `.gitignore`) via `os.environ.setdefault` (real environment wins); the loader tolerates UTF-16/UTF-8-BOM files because PowerShell redirects write UTF-16. The key itself is created at console.mistral.ai → workspace → API keys (ADR-12).
- Consequences: + one-time setup, works in every new shell; + repo stays secret-free; − A1/A5 need the `.env` to exist (README documents it); steady-state commands (A2–A4) need no key at all.

### ADR-15 — Making A1 reliable on a small model: schema in the task + deterministic normalization + bounded loop
- Status: implemented and live-tested against the Mistral API
- Context: the first live `draft` run with `mistral-small-latest` hit the 5-iteration cap; later drafts put `properties`/`support` as YAML mappings where ODCS v3 requires lists.
- Decision: (a) the table schema is introspected deterministically (`PRAGMA table_info`) and put into the task message, so the LLM loop typically needs 0–2 tool calls; (b) `MAX_TOOL_ITERATIONS = 8`; (c) `odcs.normalize_contract()` deterministically repairs list-vs-mapping slips before validation — the ODCS JSON schema remains the hard gate; (d) only valid drafts are written; an invalid draft leaves the previous contract file untouched; (e) a YAML change to an approved contract flips it back to `draft` on `sync` (re-approval).
- Consequences: + live end-to-end draft verified (artifact kept at `out/demo/draft_customers_llm.yaml`) while the manifest-aligned hand-written contracts stay the active set; − normalization is a repair layer, not a substitute for schema validity. Measured cost of the LLM experiments so far: ~$0.02 total (see `llm_calls`).

### ADR-16 — A2 executor semantics (capability B)
- Status: implemented and verified
- Decision: only `status='active'` contracts run; one `RUNNING` run per contract (lock); each rule produces one `check_results` row (status PASS/FAIL/ERROR, rows_affected, sample of ≤5 offending keys, the exact SQL executed); issues are deduped by `fingerprint = sha1(contract:rule)` — repeat failures bump `occurrences` instead of duplicating; run statuses RUNNING/COMPLETED/COMPLETED_WITH_ERRORS/FAILED/SKIPPED; after each run `next_run_due += dqScheduleMin`; everything executes on the read-only source connection.
- Verified: 5 manual runs → COMPLETED with 28/28 rules failing (= every seeded defect detected once); re-run dedups (occurrences=2, still 28 open issues); `tick` ran a due contract with `triggered_by='schedule'`; a draft contract is skipped with a logged reason.
- Consequences: + history/trend for capability C comes free from `runs`/`check_results`; + all guardrails structural; − SQLite single-writer is fine at demo scale (noted for §6 scale).

### ADR-17 — Capability E: LLM suggests, human decides, orchestrator executes
- Status: implemented and live-tested
- Decision: A5 explores an issue with read-only tools only (`query_state`, `run_sql_readonly`) and returns constrained JSON (`proposed_action ∈ {no_data_change, flag_for_human, propose_write_back}`; a write-back requires a single UPDATE/DELETE/INSERT and high confidence, else it degrades to `flag_for_human`). The HITL gate records accept/reject/close in `issue_decisions`. Only an accepted write-back is executed — by the deterministic orchestrator, in a single transaction, on the source DB (the one place that opens it read-write); afterwards A2 re-runs the contract to verify the fix. If the LLM is unavailable, a deterministic template suggestion is stored instead (disclosed).
- Verified: LLM-resolved issue (flag_for_human → RESOLVED); approved write-back (loans.term_months 0→12) executed, issue RESOLVED, re-run shows the rule PASS.
- Consequences: + satisfies "no change to source data without explicit human approval" structurally; + closed loop (fix → re-check); − demo mutates the seeded DB, so the demo flow reseeds first (PHASES.txt).

## 6. Success metrics, cost, scale (measured on this build)

- KPIs (measured):
  1. **Detection rate vs. own manifest: 100%** — 28/28 seeded defects found, 0 missed, 0 false
     positives; detected row counts equal manifest counts on every defect
     (`out/detection_report_summary.txt`, `out/detection_report.csv`).
  2. **Contract coverage: 5/5** tables have an active, human-approved ODCS v3.0.0-valid contract.
  3. **End-to-end pipeline: 1.04 s wall time** for 5 contracts / 28 rules incl. dashboard,
     marketplace and 28 notifications (single laptop process, no server).
- Cost per run (measured via the `llm_calls` table): a **steady-state scheduled run costs $0 LLM** —
  A2/A3/A4/orchestrator are deterministic. One A1 contract draft = 2 calls / 8,029 tokens
  ≈ **$0.0016** at mistral-small-latest list prices; A5 costs similarly per resolved issue.
  LLM cost scales with *new contracts and resolved issues*, never with scheduled runs.
- What breaks at 500 contracts / 50 data sources: the single-process SQLite writer and one
  serial tick become the bottleneck (≈ 500 contracts × ~10 rules × ~20 ms ≈ minutes per tick —
  still fine if batched); `check_results`/`issues` grow ~rules×runs, so add indexes on
  `check_results(run_id)` and `issues(status)` and prune old runs. Fix: keep contracts as the
  source of truth, move the run queue into a table and parallelize A2 workers per data source;
  at 50 sources on separate DBs, point each contract's `servers` entry at its own connection.
  LLM cost and agent design do not change — the agents stay ephemeral and the orchestrator
  stays deterministic.

## 8. Task 2 — justification (answers to the brief's questions)

**Why this split into agents is better than one agent or a classic non-agentic script.**
One LLM agent would either run the checks through the model (non-deterministic, costly, and it
could invent rules — exactly what the brief forbids) or do everything without tools. A classic
script (our A2+A3+A4+orchestrator alone) detects issues but cannot *draft contracts at scale*
(A1) or *help a steward resolve an issue interactively* (A5). The split puts the LLM only where
the work is genuinely fuzzy (drafting contract prose, root-cause hypotheses) and code where
correctness is checkable (execution, routing, publishing). Evidence: `grep -r mistral src/dq`
shows the LLM client is imported only by `agents/base.py` (used by A1/A5); A2–A4 override
`run()` with pure SQL. See ADR-04/05/06.

**Where deterministic code is used instead of an LLM on purpose.** Rule compilation and
execution (ADR-06), scheduling/routing (ADR-04), blackboard state (ADR-11), scoring and
dashboard aggregation, notification templating, marketplace publishing, the detection report,
and the single write-back path (ADR-17). The LLM is used only in A1/A5 and its output is always
structurally constrained (ODCS schema validation; JSON enum for `proposed_action`).

**Measurable product KPIs** — see §6: detection rate vs. own manifest (100%, target met),
contract coverage (5/5), end-to-end runtime + cost per run (1.04 s, $0 steady-state LLM).

**How we prevent the failure modes the brief names.**
- *Agents inventing rules*: checks come only from active contracts; `rules.py` fails loudly on
  unknown rule types; the LLM never generates execution SQL (ADR-06).
- *Misrouting notifications*: A4 reads recipients only from the contract's `team` section; the
  channel is a simulated file/JSON per the brief (ADR-08).
- *Exposing sensitive data*: agents open the source read-only; LLM tools return ≤50-row
  samples; bulk row data never enters a prompt — all row-level analysis is SQL (ADR-05/06);
  the API key never leaves env/`.env` (ADR-12/14).

**Options considered** (each with ADR): SQLite+stdlib vs. Postgres/FastAPI (ADR-10); deterministic
orchestrator vs. LLM supervisor (ADR-04); blackboard vs. message bus (ADR-11); Mistral API vs.
local Ollama fallback (ADR-05); ODCS v3.0.0 vendored schema (ADR-13); fixed as-of date for the
seeded dataset (ADR-03); simulated notification/marketplace channels (ADR-08).

**MVP line and courage of scope**: capabilities A–D plus E, on 5 tables, with CLI as the
interface, static HTML dashboard, JSON notifications/marketplace — per the brief's explicit
steer away from UI polish. The dataset is self-built and fictitious (ADR-01), 28 defects across
7 dimensions (ADR-02).
