# Design Decision Record — Contract-Driven Data Quality Monitor

This file (plus README) is the "Design Decision Record" deliverable from section 5 of the
brief. Each entry is an ADR: context, decision, alternatives, consequences.
Status: all decisions below are `[implemented]` and verified — see PHASES.txt for the
build log and `python run.py report` for the measured results.

---

## 1. Vision & scope

Turn data contracts (ODCS v3.x YAML) into the single source of truth for "good data":
AI agents create contracts (human-approved), execute the contract's quality rules
against SQL sources, visualise issues with history, notify owner/steward from the
contract, and publish a quality score to a (simulated) marketplace.

Scope: capabilities A–E end-to-end on a self-built fictitious SQLite banking dataset,
CLI as the interface, static HTML dashboard, JSON notifications/marketplace — per the
brief's explicit steer away from UI polish and infrastructure.

## 2. Target architecture

```
[User / Scheduler Trigger]
            |
            v
  [0. Orchestrator (Supervisor)]   <- deterministic Python router, not an LLM
            |
   +--------+--------+-----------+------------------+
   |        |        |           |                  |
   v        v        v           v                  v (optional)
[A1        [A2       [A3         [A4                [A5
Contract   Quality   Metrics &   Notify &           Issue
Architect] Executor] Insights]  Marketplace]       Resolver]
   |                                        |           |
[HITL gate:                          [HITL gate:
 approve contract]                   approve fix before
                                     any write-back]
```

Agents communicate through a shared SQLite "blackboard" (`dq.db`: `contracts`, `runs`,
`check_results`, `issues`, `notifications`, `marketplace_entries`, `steps`), not by
passing messages (ADR-11). The source database is a separate file opened read-only.

## 3. Agent personas

| # | Agent | Goal | Inputs → Outputs | Tools | Guardrails | HITL |
|---|---|---|---|---|---|---|
| A1 | Contract Architect | Draft an ODCS v3.x contract per table | schema (introspected) + business context → contract YAML | read schema, validate ODCS, write contract | contract must validate against ODCS v3.x; cannot activate itself | human approves before `status: active` |
| A2 | Quality Executor | Run contract rules against SQL, store history | active contracts → run + per-rule results | run SQL (read-only), insert results | may only execute rules present in an *active* contract; read-only on source tables | none |
| A3 | Metrics & Insights | Aggregate results into dashboard + trends | runs/results → static HTML dashboard | run SQL, write files | read-only; no new rules | none |
| A4 | Notify & Marketplace | Actionable notification + marketplace score | issues + contract → notification JSON + marketplace.json | write files/JSON | may only notify owner/steward addresses from the contract; channel simulated | none |
| A5 | Issue Resolver (optional) | Suggest root cause/fix | issue → suggestion + proposed action | run SQL (read-only), read contract | never writes to source data without recorded human approval | human accepts/rejects/closes |

The LLM is present only inside A1 and A5 (`grep -r mistral src/dq`: the HTTP client is
imported only by the shared agent base used by A1/A5; A2–A4 are pure SQL/files).

## 4. Decision log (ADRs)

### ADR-01 — Dataset: self-built fictitious banking DB in SQLite, generated by a script
- Context: the brief provides no data and asks for a small fictitious dataset (5 related tables recommended).
- Decision: 5 related tables (`customers`, `accounts`, `transactions`, `loans`, `cards`) with FK relationships; base data deterministic (`random.Random(42)`); defects inserted explicitly and commented with defect IDs (`data/seed_dataset.py`).
- Alternatives: download a public benchmark; Excel files.
- Consequences: + fully reproducible, defects known by construction, SQLite needs no server; − must self-document that data is fictitious; − SQLite FKs are not enforced at insert time, which is exactly what allows orphan-FK defects to exist for the DQ layer to catch.

### ADR-02 — Defect seeding & manifest: 28 defects / 36 defective rows, counts measured not asserted
- Context: the brief requires ≥10 seeded defects across quality dimensions plus a defect manifest (table, column, defect type, rows affected).
- Decision: 28 defects across 7 dimensions (completeness, uniqueness, validity, consistency, timeliness, accuracy, integrity). Each manifest row carries the SQL that identifies it; `rows_affected` is the actual `COUNT(*)` after seeding, never a hard-coded number (`data/defect_manifest.csv`).
- Alternatives: hard-coded expected counts.
- Consequences: + the manifest can never drift from the data; + every defect is provably detectable by one query.

### ADR-03 — Fixed as-of date for all time-based checks
- Context: with wall-clock "now", clean rows age into defects (e.g. cards expiring), so the detection report would change between runs.
- Decision: all time-based rules (future dates, expiry, under-18) evaluate against a fixed as-of date (`AS_OF = "2025-06-30"`); each run is still stamped with its own real timestamp.
- Alternatives: `date('now')`; reseeding on every run.
- Consequences: + the found/missed/false-positive comparison is stable and reproducible for graders; − deliberate demo simplification, noted as such.

### ADR-04 — Orchestrator is deterministic Python, not an LLM
- Context: the brief demands an agentic implementation but rewards using deterministic code over an LLM on purpose; the demo must run reliably.
- Decision: the Orchestrator is a plain Python router over a fixed pipeline (contracts → run checks → metrics → notify, plus optional resolve), with per-contract schedules read from the contract SLA. LLMs live only inside agents A1/A5 at the fuzzy steps. All routing, rule execution, aggregation and publishing is deterministic code. State goes through SQLite (ADR-11).
- Why not an LLM supervisor:
  1. There is nothing to decide at the top level — the flow is a fixed DAG, not a judgment call. An LLM there adds variance, not value.
  2. Guardrails become structural: "only active contracts", "read-only SQL on sources", "HITL before any write-back" are enforced by code. Prompts are probabilistic; code is not.
  3. Reproducibility: same inputs → same run, every time; graders re-running from the README get identical behaviour.
  4. Cost and latency: zero tokens for orchestration.
  5. Debuggability: a `steps` log table plus normal tracebacks, instead of an opaque, possibly looping supervisor.
- Super simple example:

  ```python
  # orchestrator.py — no LLM anywhere in this file
  STEPS = [contract_architect, quality_executor, metrics, notifier]  # fixed order

  def main(trigger="manual"):
      for contract in due_contracts(trigger):      # status=active, schedule due
          for step in STEPS:
              step.run(contract)                   # agents read/write SQLite; A1 blocks on human approval
              log_step(contract, step.name, "ok")
  ```
- Alternatives: LLM supervisor choosing the next step dynamically; heavy agent frameworks (LangChain/CrewAI) — skipped deliberately: a hand-rolled bounded loop is lighter and easier to audit.
- Consequences: + reliable, cheap, auditable, structurally safe; − the top level looks less "autonomous" (accepted: autonomy lives inside each agent's tool-calling loop).

### ADR-05 — Runtime LLM: Mistral API (`mistral-small-latest`), tool calling via stdlib HTTP
- Context: the brief allows any LLM with full disclosure (see §6).
- Decision: agents call `https://api.mistral.ai/v1/chat/completions` with tool calling, implemented with stdlib `urllib.request` in a single module (`src/dq/mistral.py` — the only file that performs HTTP). Fallback if the API is unreachable: point the same code at a local Ollama model by swapping base URL + model.
- Alternatives: local-only models from the start; other providers' free tiers.
- Consequences: + no GPU/RAM pressure, cheap per call (measured in §5); − needs internet + API key at runtime for A1/A5 only.

### ADR-06 — Guardrail: contracts drive all checks; no rules hard-coded outside contracts
- Context: capability B explicitly: "Contracts drive the checks — no rules hard-coded outside the contract."
- Decision: the Quality Executor compiles each active contract's `quality.rules[]` into SQL at run time; unknown rule types fail the run loudly. The LLM is never asked to invent rules — A5 only describes/prioritises what A2 flagged.
- Alternatives: LLM writes SQL per run (flexible but unaccountable and costly).
- Consequences: + auditable, deterministic, cheap; + directly answers the brief's "prevent agents from inventing rules".

### ADR-07 — HITL gates exactly where the brief demands human approval
- Context: capability A requires human review before a contract becomes active; capability E forbids writes to source data without explicit human approval.
- Decision: two HITL gates — (1) after A1 drafts a contract, `ask_human()` blocks until approve/reject (recorded in the DB; `--auto-approve` flag exists for the recorded demo); (2) A5's proposed fix requires accept/reject/close before any write-back.
- Alternatives: no gates (rejected — violates the brief); gates on every check run (too noisy).
- Consequences: + directly satisfies the brief; + approvals are auditable rows in the DB.

### ADR-08 — Notifications & marketplace are simulated as files
- Context: capability D explicitly allows simulated channels ("a generated page or JSON catalogue").
- Decision: A4 writes `out/notifications/<issue_id>.json` (to owner+steward taken from the contract) and `out/marketplace.json` with a per-product quality score/status; A3 renders a static `out/dashboard.html`.
- Alternatives: real email/Slack webhooks; hosted marketplace page.
- Consequences: + zero infrastructure, works offline, easy to demo; − stated clearly as simulated per the brief.

### ADR-09 — Detection report produced by a deterministic diff against the defect manifest
- Context: Task 1 requires comparing detected issues with the defect manifest (found / missed / false positives); the deliverable is an Excel tab (seeded defect, rule, detected Y/N, severity).
- Decision: `compare_to_manifest.py` matches the latest run's issues to `data/defect_manifest.csv` 1:1 by rule mapping and emits `out/detection_report.csv` / `.xlsx` plus a summary with an honest miss/false-positive analysis.
- Alternatives: manual comparison in Excel.
- Consequences: + reproducible, honest reporting; − rule naming must stay 1:1 with manifest defects.

### ADR-10 — Stack: Python + SQLite + stdlib only (plus `pyyaml`, `jsonschema`)
- Context: must run on low/medium hardware with minimal dependencies.
- Decision: no web framework, no ORM, no `requests`; SQLite via stdlib `sqlite3`; dashboard = static HTML; contracts = YAML (`pyyaml`); ODCS validation via `jsonschema`.
- Alternatives: FastAPI + requests + ORM + Postgres.
- Consequences: + runs anywhere, boots instantly, nothing to break on demo day; − more boilerplate, acceptable at this scale.

### ADR-11 — Agents communicate through a SQLite "blackboard", not messages
- Context: agents must hand work to each other (A2's results → A3's dashboard; issues + contract → A4's notifications) without tight coupling.
- Decision: no agent calls another agent. Each agent reads inputs from and writes outputs to shared tables in one SQLite file. Flow: A1 inserts a contract row (after HITL) → A2 inserts `runs`/`check_results` → A3 SELECTs them for the dashboard → A4 SELECTs `issues` JOIN `contracts` for owner/steward, then writes notifications + marketplace.
- Why: decoupling (retry one step without redoing the pipeline); free history (trend view = query over past runs); auditability (approvals are rows); crash-safety (resume from the last completed `steps` row); zero infra.
- Alternatives: direct agent-to-agent calls or a message bus (Redis/RabbitMQ/framework messages).
- Consequences: + simple and robust; − requires schema discipline: `schema.sql` defines all tables, each agent writes only its own.

### ADR-12 — Credentials: the LLM API key comes from the environment, never from the repo
- Context: the brief's failure-mode list includes exposing sensitive data; the repo will be published.
- Decision: runtime agents read `MISTRAL_API_KEY` from the environment only; a repo-root `.env` (gitignored) is loaded as a fallback via `os.environ.setdefault`, so the real environment always wins. Keys are created in the Mistral console (console.mistral.ai → workspace → API keys); no secret is ever committed. Setup is documented in README.
- Alternatives: hard-coding the key in code (rejected — leaks into git history).
- Consequences: + the repo is safe to publish; + rotation is a one-line env change; − A1/A5 require the env var (steady-state commands A2–A4 need no key at all).

### ADR-13 — Contracts validated against the official ODCS v3.0.0 JSON Schema (vendored)
- Context: the brief requires contracts "compliant with ODCS v3.x"; graders check validity against the ODCS schema.
- Decision: the official schema from bitol-io/open-data-contract-standard is vendored at `src/dq/odcs-json-schema-v3.0.0.json`; every `contracts/*.yaml` is validated against it with `jsonschema` at `python run.py sync`, plus semantic checks (table/columns must exist in the source DB, rule names unique). Rules use ODCS-native constructs (`type: library` at property level, `type: sql` with `${table}`/`${asOf}` placeholders). 28 rules across 5 contracts = exactly the 28 manifest defects.
- Schema learnings: top-level `description` must be an object, not a string; the `dimension` enum has no `validity`/`integrity`, so those map to ODCS `conformity`/`consistency`.
- Consequences: + contracts provably schema-valid offline; + editing an approved contract flips it back to `draft` on `sync` (re-approval, HITL); − pins us to v3.0.0 specifically (brief allows any v3.x).

### ADR-14 — Making A1 reliable on a small model: schema in the task + deterministic normalization + bounded loop
- Context: early live drafts with `mistral-small-latest` needed several tool iterations and occasionally produced YAML shapes that violate ODCS v3.
- Decision: (a) the table schema is introspected deterministically (`PRAGMA table_info`) and put into the task message, so the loop typically needs 0–2 tool calls; (b) `MAX_TOOL_ITERATIONS = 8`; (c) `odcs.normalize_contract()` deterministically repairs list-vs-mapping slips before validation — the ODCS JSON schema remains the hard gate; (d) only valid drafts are written; an invalid draft leaves the previous contract untouched.
- Consequences: + live end-to-end draft verified (artifact at `out/demo/draft_customers_llm.yaml`) while the manifest-aligned contracts stay the active set; − normalization is a repair layer, not a substitute for schema validity.

### ADR-15 — A2 executor semantics (capability B)
- Decision: only `status='active'` contracts run; one `RUNNING` run per contract (lock); each rule produces one `check_results` row (PASS/FAIL/ERROR, rows_affected, ≤5-row sample, exact SQL executed); issues deduped by `fingerprint = sha1(contract:rule)` — repeat failures bump `occurrences`; after each run `next_run_due` advances by the contract's schedule; everything executes on the read-only source connection.
- Verified: 5 runs → COMPLETED with 28/28 rules failing (= every seeded defect detected); re-run dedups (occurrences=2, still 28 open issues); `tick` runs due contracts with `triggered_by='schedule'`; a draft contract is skipped with a logged reason.
- Consequences: + history/trend for capability C comes free; + all guardrails structural; − SQLite's single writer is fine at demo scale (see §5 for scale).

### ADR-16 — Capability E: LLM suggests, human decides, orchestrator executes
- Decision: A5 explores an issue with read-only tools only and returns constrained JSON (`proposed_action ∈ {no_data_change, flag_for_human, propose_write_back}`; a write-back requires a single UPDATE/DELETE/INSERT and high confidence, else it degrades to `flag_for_human`). The HITL gate records accept/reject/close in `issue_decisions`. Only an accepted write-back is executed — by the deterministic orchestrator, in a single transaction, on the source DB (the one place that opens it read-write); afterwards A2 re-runs the contract to verify the fix. If the LLM is unavailable, a deterministic template suggestion is stored instead (disclosed).
- Verified: LLM-suggested resolution (flag_for_human → RESOLVED) and an approved write-back (loans.term_months 0→12) executed, issue RESOLVED, re-run shows the rule PASS.
- Consequences: + "no change to source data without explicit human approval" is structural; + closed loop (fix → re-check); − the demo mutates the seeded DB, so the demo flow reseeds first.

### ADR-17 — MCP (Model Context Protocol) considered and deliberately not used
- Context: the brief allows any agent tooling; MCP is the common way to expose tools to LLM clients via tool servers.
- Decision: not used. Our agents call six small Python functions directly from our own loop (`tools.py`), because (a) the tools are trivial (SQLite, files, `input()`), (b) the guardrails must live in code regardless of protocol — read-only source connection, contract-only notification recipients, HITL — so an MCP layer would add processes and indirection without adding safety, (c) it keeps the demo reproducible and light on low/medium hardware.
- When MCP would be the right choice: running the agents inside an MCP-capable host instead of our own loop, sharing tool servers across multiple clients, or integrating external systems without writing clients.
- Consequences: + minimal moving parts, guardrails grep-able in one file; − no access to MCP's ecosystem of prebuilt servers (acceptable at this scope).

## 5. Success metrics, cost, scale (measured on this build)

- KPIs (measured):
  1. **Detection rate vs. own manifest: 100%** — 28/28 seeded defects found, 0 missed, 0 false positives; detected row counts equal manifest counts on every defect (`out/detection_report_summary.txt`, `out/detection_report.csv`, `.xlsx`).
  2. **Contract coverage: 5/5** tables have an active, human-approved, ODCS v3.0.0-valid contract.
  3. **End-to-end pipeline: 1.04 s wall time** for 5 contracts / 28 rules incl. dashboard, marketplace and 28 notifications (single laptop process, no server).
- Cost per run (measured via the `llm_calls` table): a **steady-state scheduled run costs $0 LLM** — A2/A3/A4/orchestrator are deterministic. One A1 contract draft = 2 calls / 8,029 tokens ≈ **$0.0016** at mistral-small-latest list prices; A5 costs similarly per resolved issue. LLM cost scales with *new contracts and resolved issues*, never with scheduled runs.
- What breaks at 500 contracts / 50 data sources: the single-process SQLite writer and one serial tick become the bottleneck (≈ 500 contracts × ~10 rules × ~20 ms ≈ minutes per tick — still fine if batched); `check_results`/`issues` grow ~rules×runs, so add indexes on `check_results(run_id)` and `issues(status)` and prune old runs. Fix: keep contracts as the source of truth, move the run queue into a table and parallelise A2 workers per data source; at 50 sources on separate DBs, point each contract's `servers` entry at its own connection. LLM cost and agent design do not change.

## 7. Task 2 — justification (answers to the brief's questions)

**Why this split into agents is better than one agent or a classic non-agentic script.**
One LLM agent would either run the checks through the model (non-deterministic, costly, and it could invent rules — exactly what the brief forbids) or do everything without tools. A classic script (our A2+A3+A4+orchestrator alone) detects issues but cannot *draft contracts at scale* (A1) or *help a steward resolve an issue interactively* (A5). The split puts the LLM only where the work is genuinely fuzzy (drafting contract prose, root-cause hypotheses) and code where correctness is checkable (execution, routing, publishing). Evidence: `grep -r mistral src/dq` shows the LLM client is used only by the agent base of A1/A5; A2–A4 are pure SQL. See ADR-04/05/06.

**Where deterministic code is used instead of an LLM on purpose.** Rule compilation and execution (ADR-06), scheduling/routing (ADR-04), blackboard state (ADR-11), scoring and dashboard aggregation, notification templating, marketplace publishing, the detection report, and the single write-back path (ADR-16). LLM output is always structurally constrained (ODCS schema validation; JSON enum for `proposed_action`).

**Measurable product KPIs** — see §5: detection rate vs. own manifest (100%), contract coverage (5/5), end-to-end runtime + cost per run (1.04 s, $0 steady-state LLM).

**How we prevent the failure modes the brief names.**
- *Agents inventing rules*: checks come only from active contracts; `rules.py` fails loudly on unknown rule types; the LLM never generates execution SQL (ADR-06).
- *Misrouting notifications*: A4 reads recipients only from the contract's `team` section; the channel is a simulated file/JSON per the brief (ADR-08).
- *Exposing sensitive data*: agents open the source read-only; LLM tools return ≤50-row samples, bulk row data never enters a prompt — row-level analysis is SQL (ADR-05/06); the API key never leaves env/`.env` (ADR-12).

**Options considered** (each with an ADR): SQLite+stdlib vs. Postgres/FastAPI (ADR-10); deterministic orchestrator vs. LLM supervisor (ADR-04); blackboard vs. message bus (ADR-11); Mistral API vs. local-model fallback (ADR-05); vendored ODCS v3.0.0 schema (ADR-13); fixed as-of date for the seeded dataset (ADR-03); simulated notification/marketplace channels (ADR-08); MCP vs. direct tool functions (ADR-17).

**Scope**: capabilities A–E on 5 tables, CLI interface, static HTML dashboard, JSON notifications/marketplace, self-built fictitious dataset with 28 defects across 7 dimensions (ADR-01/02) — per the brief's steer away from UI polish.
